# Architectural Blueprint: Neuro-Symbolic DAG Orchestrator

## 1. Core Philosophy
This framework bridges the probabilistic freedom of Large Language Models with the deterministic rigor of Graph Theory. It replaces brittle string-matching (Symbol Tables) with a **Hierarchical Masked Macro-Attention System**, turning the Python Orchestrator into the physical attention mechanism for the graph.

* **The Planner LLM:** Determines topology (The "When") and generates natural language queries for what it needs. Operates on a "blank canvas."
* **The Worker LLM:** A blind, stateless arithmetic/logic unit. It never sees the graph topology, only the exact injected context.
* **Neo4j Graph (The KV Cache):** Stores the immutable executed outputs and the strict topological execution paths.
* **Python Orchestrator:** Acts as the traffic cop. It performs the mathematical routing, applies topological masks, and shuttles data between Neo4j and the Worker LLMs.

---

## 2. The Macro Q, K, V System
Instead of forcing the LLM to invent and remember variable names (e.g., `[Data_Node_X]`), we map the Transformer’s native QKV logic onto the DAG.

* **Macro Key ($K$):** Generated by the Planner when defining a task. It consists of the topological ID, the namespace, and a description of what the task creates.
* **Macro Value ($V$):** The actual JSON payload resulting from the Worker LLM's execution (e.g., `{"x": 10, "y": 20}`).
* **Macro Query ($Q$):** Generated by a downstream task to request data (e.g., *"I need the top-face coordinate"*).

---

## 3. Resolving Semantic Dilution (The Math)

To prevent the system from confusing identical semantic concepts (e.g., mixing up "Point A" and "Point C" which both embed as "3D coordinate"), the Orchestrator uses two mathematical interventions.

### Intervention A: Topological Masking ($M$)
Prevents cross-contamination between parallel branches.

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{Q K^T}{\sqrt{d_k}} + M\right)V$$

* **$M = 0$**: If the Key is a direct topological ancestor of the Querying task (Allowed).
* **$M = -\infty$**: If the Key belongs to a parallel or unrelated branch (Forbidden). This forces the softmax probability of unrelated branches to exactly $0.0\%$.

### Intervention B: Anchor Vectors (Combatting Intra-Branch Drift)
Prevents confusion between similar nodes within the same vertical lineage. The Planner must assign an orthogonal, categorical **Anchor** to every Key and Query.

$$S = \alpha \cdot \cos(Q_{\text{semantic}}, K_{\text{semantic}}) + \beta \cdot \delta(Q_{\text{anchor}}, K_{\text{anchor}})$$

* **$S$**: The final alignment score used for routing.
* **$\cos$**: Cosine similarity of the embedded natural language strings.
* **$\delta$**: Kronecker delta (returns $1$ if Anchors match perfectly, $0$ if they do not).
* **$\alpha, \beta$**: Tuning weights (e.g., $\alpha = 0.3, \beta = 0.7$ to heavily enforce the Anchor lock).

---

## 4. Hierarchical Grouped-Query Attention (Macro GQA)
To avoid $O(N^2)$ computation across the entire database, the DAG is broken into **Namespaces** via the `DECOMPOSE` flag.
* When a massive task is flagged for `DECOMPOSE`, it spawns a new Namespace Group (e.g., "Group Alpha").
* Queries generated inside Group Alpha only calculate attention against Keys within Group Alpha (and its direct parent inputs).
* This creates infinite scalability with zero context-window explosion.
